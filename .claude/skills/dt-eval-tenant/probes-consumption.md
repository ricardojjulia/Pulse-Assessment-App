## §D — Effective Consumption KPIs (`dtctl query`, DQL — the "is it being *used* well" pillar)

Optional pillar that grades **effective consumption**, not just configuration: automation that executes, self-service that is distributed, problems that are useful, data that is queried. Full derivation, per-KPI DQL, computability tags, and the OES rollup live in **[effective-consumption.md](effective-consumption.md)**; the importable, sectioned version is **[effective-consumption-notebook.json](effective-consumption-notebook.json)**. All queries below were live-validated (a live reference tenant, 30-day windows, 2026-07-10). Windows are 30d (behavioral trend); `dt.system.events` is large (millions of rows) but system-scoped and cheap — no unscoped-log guardrail applies, but keep the `event.kind`/`event.type` filters that make each scan selective.

(IDs are **EC1–EC17** — the plain `D1–D6` above are the unrelated deep-dive recipes, now in [probes-deepdives.md](probes-deepdives.md).)

**Interpretation rules that need judgment (where this pillar earns its keep):**

- **Cross-correlate, don't just report.** WFR *next to* the workflow inventory (A4/A5): a low WFR with dozens of scheduled workflows = polling automation that mostly fails — name the workflows. PUI's near-zero impact-cardinality *next to* B4/B7: almost-all-single-entity problems ⇒ shallow topology or per-entity static thresholds, not Davis correlation. **QEI (active engagement) *next to* B14 ingest**: huge ingest + few *sustained* users = shelfware — measure it as the share of human users who query on ≥10 distinct days, and weigh sustained-user count against estate size (§B host count); **never** score engagement by bucket/table diversity (it trivially maxes out and hides shelfware) or by scanned-bytes (repeated/broad scans inflate it).
- **`isNull(authentication.token)` is the human/automation switch.** It removes token- and Terraform/Monaco-driven changes so COC/SSU reflect *human* self-service; **EC8/CCS is the inverted measurement** — the token-driven share of *all* changes is the config-as-code signature (target ≥ 0.7; the reference tenant validated at **0.008** = click-ops estate). CCS joins WFR/WOS in the Automation pillar (composition change flagged in the method — see effective-consumption.md).
- **Fence outlier actors before any distribution KPI (median + 3×IQR).** One terraform-runner under a user identity can dwarf every human combined; fence per-actor counts at `p50 + 3×(p75−p25)`, name fenced actors in a side-note, exclude them from COC/SSU/QEI, count them toward CCS. Same rule for every hotspot list (top config types, top buckets, top users). "No outliers fenced" is method color, not a finding.
- **Carry a confidence flag per pillar** (High ≥ 100-denominators / Medium 30–100 or 1–2 ⚪ / Low < 30 or majority ⚪) — a thin denominator must never read as a firm grade. **EUB (EC9) is context for QEI, never an OES input** — it rests on persona-count assumptions (standards-overridable) and is always presented as an estimate.
- **Config↔events stitch (EC7) beats either surface alone.** Events only see workflows that *ran*; config (`get workflows`) sees all — including dormant ones. On the validation tenant, 90 workflows were configured but only 42 ever executed, and **5 davis-problem workflows had zero runs against ~30k problems** (4 `isActive:false`, 1 active-but-never-fired). Config alone says "one is active"; events alone show nothing; only the stitch exposes the dead alerting→automation lane. Inject the davis-problem id set into EC2 to get problem-attached WFR and the SQI workflow leg, and name the offending workflows. **The stitch runs in BOTH directions:** configured-but-never-executed (above) *and* **executed-but-no-longer-configured** — executing workflow titles in the event stream that are absent from `get workflows` are workflows deleted or renamed inside the window (live 2026-07-28: 8 executing titles vs 7 configured workflows, the extra one a family of deleted billing-integration variants). That divergence is a governance signal the config surface cannot see — automation ran that nobody can now inspect, review, or re-run; report it, don't reconcile it away.
- **Gen3-first governs the Foundation KPIs (D5).** The source model's FCS rewards management zones + classic tags; the skill rule (SKILL.md, Phase 4) forbids scoring classic-construct absence as a gap. **Reframe FCS/SCI/MCS to platform-native surfaces** — host groups, segments, buckets, source tags (B5) — and never recommend creating classic constructs. 0 MZs + segments + source tags = high foundation, not low.
- **Partial / definition-gated KPIs follow the ⚪ rule.** SQI (needs ITSM ticketing), SQ-BLP coverage (needs an entity-consumption definition), and SCI/FCS/MCS (need the customer's required-tag / id-env-owner standard) are **excluded from the OES denominator and reweighted**, never scored 0 — appendix footnote names the input that would include each next time.
- **Weighting is a documented source ambiguity.** The notebook states two conflicting weight sets (prose: Signals .35 / Auto .20 / Foundation .10 / Engagement .35; code: .35 / .35 / .20 / .10). Default to the **code-block** weights, expose them as notebook variables, and flag the choice — never bury it.
- **Never grade automation on reliability alone (owner correction, 2026-07-14, large estate).** WFR 98.9% + raw CCS ~0.84 produced an "automation excellence" verdict on an estate whose 9 workflows were scheduled platform-tending and whose token changes were integration churn (agent-update + ~80 maintenance-window writes/day; zero declarative actors). Run EC10 (CCS decomposition) and EC14 (footprint) before scoring the pillar: `Automation = mean(WFR, WOS, FPR, CCS-Q)`. A daily maintenance-window-writing integration is its own hygiene finding — cross-check EC3's `underMaint` share (windows churning while 0% of problems fire under maintenance = windows that may scope nothing).
- **Diagnose PUI with SMX (EC11), not just topology.** 71% CUSTOM_ALERT share = the problem stream is ported thresholds — Davis RCA structurally can't attach. Read alongside B3 (mode split): both feed the same finding from independent directions. The same probe yields per-category durations and routing-intent coverage (`labels.alerting_profile`); intent set + 0 classic notifications + 0 problem-workflow runs = orphaned routing — caveat that external API pollers are invisible to every in-tenant surface.
- **AI consumption (EC12) is presence + health, not a score.** Analyzer executions = Gen3 AI running; `SUCCESSFUL_WITH_WARNINGS` is a three-valued status — a large warnings share is *degraded, not failing* (report it as tuning opportunity). GENAI_EVENT/CoPilot invocations are adoption color (no populated user.id — count volume/days, never users). Neither joins the OES.
- **Fence machine actors from QEI (EC15) — signature decides, never volume alone.** External pollers (SLO tools, scripts) run under user identities with `internal_service_context` null; signature = high volume + 1–3 distinct `client.client_context` values (humans accrue tens–hundreds via app cards). The `median + 3×IQR` volume fence only *nominates* candidates; an actor is fenced only when the signature also matches — a high-volume, high-context-diversity actor is a power user and stays in (and gets credited). Fence confirmed matches out of active/sustained, name them in the method note. QEC (EC13) is context: scan-to-ingest ratio + on-demand share tell the cost-shape story that engagement rates hide.
- **Metadata-strategy baseline makes Foundation partially scoreable WITHOUT the standards file (EC17, owner request 2026-07-14).** The full SCI/MCS pattern compliance stays definition-gated, but a **baseline-minimum standard** — does the estate identify *application*, *organization/division/LOB*, and *environment* (or equivalents) at all; are host groups actually defined; do segments work against those dimensions — needs no customer input. Read the tag-KEY inventory for the key families (exact names vary: `HGApp`/`primary_tags.application`/`[VMware]Application` are one family), read host-group names for an encoding convention (`<app>.<env>.<division>` on the large estate — the HG* tags derive from it), and **test** each segment's `variables` DQL for rows (A6 rule — defined ≠ effective). `Foundation_baseline = mean(baseline-key coverage, host-group coverage, segment effectiveness)`; large estate: mean(0.845, 0.843, 16/17) = **0.87 — a strength the old ⚪ hid**. Findings to name: the uncovered share, the same concept under parallel conventions (HG* vs primary_tags.* vs [VMware]*), case-duplicate host groups (`X.Development.MMD` vs `x.development.mmd`), placeholder segments. Gen3-first: never count management zones here.
- **Title patterns expose the rule library behind the problem stream (EC16, owner request 2026-07-14).** Group problems by `event.name` and read three things: (a) **repetition** — few distinct titles for many problems (large estate: ~1,800 titles / ~32k problems ≈ 18 each; top 10 titles = 47%, one Lambda-error rule alone = 20%) means the same rules breach over and over — the platform is being run as a threshold pager, "basically another monitoring tool"; (b) **naming convention** — severity-in-title prefixes (`APP\|MAJOR\|`, `INFRA\|MINOR\|`, `CTX\|…`) are an imported rule library from a prior tool, and their problem share should ≈ the CUSTOM_ALERT share (large estate: 70.6% vs 70.9% — the match IS the proof); (c) **top offenders** — the highest-count titles are the tuning worklist, name them. Cross-reads: EC11 category mix (same diagnosis from the category axis), B3 mode split, A2/A43 detector configs.
