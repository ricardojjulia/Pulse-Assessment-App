## §A — Configuration inventory (`dtctl get`, all read-only)

**Shell note (zsh, read before batching commands):** zsh does **not** word-split unquoted variables — `C="--context x"; dtctl $C get buckets` passes ONE malformed argument and fails with the unrelated-looking `Error: unknown command "buckets"` (one wasted probe batch, 2026-07-28). Write `--context <name>` inline in every loop, or use an array (`C=(--context x); dtctl $C get buckets`). Details in [field-notes.md](field-notes.md).

**Evaluate these settings — do not enumerate them.** Every §A probe reads a *configuration*; the deliverable is a *judgment on that configuration*, never a restatement of it. "The tenant has 19 service-detection rules / 13 Davis detectors / 5 maintenance windows" is a data dump — the failing pattern this project exists to avoid. For each config probe, produce the three things the Core directive demands: **(1) is this configuration effective?** — read the *content*, not the count (like D5 does for detectors): are the rules duplicated, near-duplicate clones, overlapping OOTB behavior, dormant/disabled, watching dead inputs, or left at platform defaults? **(2) what does it silently cost if it's wrong?** — untuned failure detection makes every span/SLO error rate untrustworthy; a standing maintenance window suppresses real alerts nobody sees; an over-split service map dilutes the correlation Davis needs; classic log rules running alongside OpenPipeline mean two systems drifting apart. **(3) the sequenced fix.** Grade bands to apply: **✅** the setting is present *and* shaped to this estate's needs; **💡** present but generic/default/partly dormant (an opportunity to tune); **⚠️** absent where the outcome demands it, or actively counterproductive (suppressing signal, inflating topology, enriching nothing). **Gen3-first still governs**: never grade the *absence* of a classic construct (classic log rules, classic detectors, management zones) as a gap — score the outcome on its platform-native mechanism. A config probe whose report line is a number and a definition is unfinished.

### A52 recipe — which service-detection rules need rework, and why (verified 2026-07-31)

**Why this matters more than its object count suggests.** Service-detection configuration decides
*what a service is*. Change it and the service topology changes — and Davis correlates over that
topology. So a broken or silently-reshaped service-detection estate moves the ground under every
service-level finding in the Config Review **and** every detector in `/dt-eval-prob`. Grade it as a
dependency, not a standalone tidy-up.

**The flag rule is Dynatrace's own, not ours** (transcribed from the upgrade-readiness dashboard).
Evaluate **enabled** objects only (`value.enabled !== false`) and flag an object when ANY applies:

| Rule family | Schema(s) | Flag when |
|---|---|---|
| Full Service Detection | `builtin:service-detection.full-web-request`, `.full-web-service` | `value.managementZones[]` non-empty → **"Management zone"** · a `value.conditions[]` entry with `attribute == "PG_Tag"` whose `tagValues[]` (when `compareOperationType == "TagEquals"`) or `textValues[]` holds any value **not** prefixed `primary_tags.` → **"Non-primary PG tag"** |
| Global Failure Detection | `builtin:failure-detection.environment.rules`, `.parameters` | a condition with `attribute == "SERVICE_MANAGEMENT_ZONE"` → **"Management zone"** · `attribute == "PG_TAG"` with any `predicate.tags[]` / `predicate.tagKeys[]` / `predicate.textValues[]` not prefixed `primary_tags.` → **"Non-primary PG tag"** · `attribute == "SERVICE_TAG"` → **"Service tag"** |

Field names verified live: `value` carries `conditions`, `enabled`, `idContributors`,
`managementZones`, `name`; a condition carries `attribute`, `compareOperationType`, `ignoreCase`,
`tagValues`. **`managementZones` is a list — test emptiness, not presence** (the key exists on
every object).

**The cited HOW, stated by Dynatrace verbatim:** remove the management-zone, service-tag and
process-group-tag scopes from these configurations; the same behavior is reproduced by using
**primary tags** from process groups in the *Process group tag* input field. This is a mechanical
rewrite with a documented target — say that, because "rework your service detection" without the
target reads as open-ended risk.

**⚪ PARTIAL COVERAGE — say so, never imply the estate was fully assessed.** Dynatrace's own check
covers four rule families; **only two are reachable from `dtctl`.** *Request Attributes* and
*Request Naming* live on the classic config API (`/api/config/v1/service/requestAttributes`,
`/api/config/v1/service/requestNaming`) with no settings schema and no `dtctl` verb (verified
2026-07-31), which puts them outside the 100 %-dtctl design. Their flag criteria — a
`dataSources[].scope.tagOfProcessGroup` not prefixed `primary_tags.`, a
`dataSources[].scope.serviceTechnology` present, a `managementZones[]` on a naming rule, or a
`SERVICE_TAG` condition — are recorded here **so the gap is specified rather than merely admitted**,
and the appendix footnote names the surface that would include them. Note both endpoints are
**VISIBLE** in [classic-to-native-map.md](classic-to-native-map.md) Table 2 — they survive the
upgrade, so the rules keep working *as API objects* while still needing the scope rework; do not
conflate "endpoint survives" with "no work required."

**Grading (E12):** 0 flagged enabled rules across the assessed families = ✅ · any flagged = ⚠️ with
each rule named and its reason(s) listed · assessed families only, with the two unassessed families
footnoted. A tenant with **0 objects** in the failure-detection schemas has no global failure-detection
rules at all — that is ✅ for that family, never ⚪ (verified live: a real tenant returned 0/0).

**Scope note — `openpipeline:configurations:read` gates the WHOLE E4 evidence base (corrected
2026-07-31 on a live least-privilege token).** An earlier version of this note said the scope was
needed only by **A29** (`classic-pipelines-translation`), the one §A read that does not go through the
settings API, and that A21/A22/A23 were fine on `settings:objects:read` because they are
`builtin:openpipeline.*` settings objects. **That is wrong.** On a platform token carrying
`settings:objects:read` but not `openpipeline:configurations:read`, **every** `builtin:openpipeline.*`
schema returns 403 — `.logs`, `.events`, `.bizevents`, `.security_events` — while
`builtin:management-zones` on the same token returns objects normally. The scope gates the
OpenPipeline settings surface, not just the translation verb.

**Why it matters more than a missing probe:** without it, E4 loses its native-target side (A21 routing,
A22 pipelines, A23 sub-configs) **and** its classic-residue side (A29) simultaneously, while every
other §A probe keeps working — so the log-processing domain goes dark with no obvious cause, on a token
that looks correctly scoped. Grade E4 ⚪ and name this scope if the OpenPipeline reads 403.

**This surfaced only because a genuinely least-privilege token was used.** The SSO contexts the
battery normally runs under carry everything, so the dependency was invisible; it appeared the first
time a token was built from the README table. Every settings read also declares
**`app-settings:objects:read`** alongside `settings:objects:read`.

**Drill-downs when a probe surfaces a problem:** `dtctl describe <resource> <id>` (any resource), `dtctl logs workflow-execution <id>` (why an A5 execution failed), `dtctl get wfe-task-result <execution-id> <task>` (per-task output).

**Considered and deliberately skipped** (so future runs don't re-litigate): `intents`/`sdk-versions`/`open`/`share` (app plumbing, not posture), `documents` (dashboards+notebooks already counted), `trash` (churn noise), `breakpoints` (dev-obs adoption — optional color at best), `hub-extension-releases` (only when grading one extension's currency), `exec *` (run-verbs — violates read-only), `alias`/`skills`/`config set*` (client-side).
