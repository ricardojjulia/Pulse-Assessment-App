## §C — REST (none — the evaluation is 100% dtctl)

**Scope decision (2026-07-09):** no curl in this evaluation. Everything once listed here proved schema- or Grail-reachable — OpenPipeline → `builtin:openpipeline.*` settings (A21–A23); security posture → `fetch security.events` (B11); consumption → `dt.billing.*` metrics (B14); OneAgent versions → `installerVersion` (B13); update policies → `builtin:deployment.*` settings (A24–A26); ActiveGate fleet/zones/health → `dt.sfm.active_gate.*` metrics (B15) — and the two stragglers were resolved by decision:

- **Classic API-token inventory — removed from scope.** Token hygiene is assessed from configuration only (A27 policy toggles). Do not curl `apiTokens`; the report's appendix states: *"API-token inventory (stale / over-scoped / never-expiring tokens) is out of scope for this evaluation."*

  **Re-examined 2026-07-31 — decision UNCHANGED, but the cost is now measurable and worth stating.** B43 (classic API usage by caller) made this the most expensive scope decision in the catalog: `user.id` reads `UNKNOWN` on token-authenticated audit rows, so **the token public ID is the only attribution available**, and the E10 remediation therefore opens with a manual step — map each token alias to an owner in Settings → Access tokens. Live: **14 and 12 distinct callers** on two tenants, each one a manual lookup. Reading `/api/v2/apiTokens` would resolve alias → name, owner, scopes, expiry and last-used in one call and collapse that step to nothing, and it would restore the token-hygiene assessment (stale / over-scoped / never-expiring) that this bullet descoped.
  **CORRECTION (2026-07-31, same day).** An earlier version of this bullet claimed *"no platform scope grants it."* **That was wrong.** The platform scope **`api-tokens:tokens:read`** exists. The claim rested on two things that do not establish a negative: `dtctl`'s readonly scope set does not *request* it, and the platform-tokens docs page does not *enumerate* scopes at all. Neither is evidence of absence, and asserting one from them was an overreach — recorded here because a confident wrong negative in a scope table is exactly the kind of thing that gets designed around for months.
  **What is actually blocking:** **`dtctl` has no verb for the token inventory** (no `tokens` resource, no raw-API passthrough — directly verified). So the gap is a *call path*, not a permission. The endpoint itself is `/api/v2/apiTokens` (classic scope `apiTokens.read` on a classic token; `api-tokens:tokens:read` on a platform token) and it is **VISIBLE** in [classic-to-native-map.md](classic-to-native-map.md) Table 2 — it survives the upgrade.
  **Recommended posture:** **grant `api-tokens:tokens:read` on the review identity now** (README lists it as worth granting) even though nothing reads it yet — it costs nothing and removes the permission half of the problem in advance. Then the remaining work is one call path, at which point B43's alias list resolves to named, owned integrations automatically and the descoped token-hygiene assessment (stale / over-scoped / never-expiring) comes back with it. **Until then**, the mitigation stands: hand the customer the alias list and let them do the lookup in their own tenant, where owner and name are already on screen.
  **What to do instead:** the endpoint `/api/v2/apiTokens` is **VISIBLE** in [classic-to-native-map.md](classic-to-native-map.md) Table 2, so it survives the upgrade and the customer can run the lookup themselves. Hand them the alias list; the mapping is theirs to do in their own tenant, where the owner and name are already on screen. **Revisit if a platform-native token-inventory surface appears** — at that point the manual step disappears and the hygiene assessment comes back for free.
- **Cluster-version reference — removed.** Currency grades on **drift within the fleet** (B13 OneAgent spread, B36 AG version spread), which needs no external "latest" reference.
- **ActiveGate version currency — HOLD LIFTED 2026-07-28** (on hold 2026-07-09 → lifted when a Grail surface appeared). History, kept because the negative shaped the design: the 2026-07-09 re-test (dtctl 0.33.0) was negative on all four surfaces — `dt.entity.active_gate` / `dt.entity.environment_active_gate` "entity type wasn't found"; `smartscapeNodes "ACTIVE_GATE"` / `"ACTIVEGATE"` empty; the full `dt.sfm.active_gate.*` dimension sweep had no version dimension; the only AG schemas were `builtin:activegate-token` and `builtin:deployment.activegate.updates` (= A25). The 2026-07-28 re-test (surfaced by the `inventory` preflight census; `playground`, dtctl 0.35.0) overturned it: **`smartscapeNodes ACTIVEGATE` (no underscore) returns the full AG fleet with `dt.active_gate.version`** — integrated as **B36** (probe + V36 verification twin + MANUAL-EXTRACTION §5 mirror), and the per-run surface re-test this bullet used to mandate is retired with it. The mandated report wording (*"AG version currency: on hold, no Grail surface yet"*) is **retired** — AG version currency is assessed, graded on drift within the fleet per the rule above. What is still **not assessed: auto-update status** — **no *query* surface exposes it** (re-verified 2026-07-31: no `dt.fleet.*` metrics, no fleet-related `event.kind`, and `smartscapeNodes ONEAGENT` returns version / monitoring-mode / network-zone but no update state; Smartscape `modules[]` containing `AUTOUPDATE` is module **presence**, not status). A25 policy remains the update-posture signal and the report must not imply update-status health. **Qualified 2026-07-31 — do not read this as 'no surface exists':** the **Fleet Management** app (`dynatrace.fleet.management`, the native successor to Deployment Status and OneAgent Health per [classic-to-native-map.md](classic-to-native-map.md) Table 1, and present on every tenant checked) clearly reads this data, behind the platform scopes **`fleet-management:activegates:read`** and **`fleet-management:oneagents:read`**. As with `api-tokens:tokens:read`, the blocker is a **call path, not a permission** — `dtctl` has no fleet verb (directly verified) and there is no DQL mirror. Grant the scopes on the review identity now (README lists them) so that when a path exists the gap closes immediately: update *status* is the missing middle between A25's *policy* and B13/B36's version *drift* — the cause, where today we report only the rule and the symptom. **This bullet previously read as an absolute absence; that phrasing is retired**, for the same reason the API-token claim above was — a confident wrong negative in a scope table gets designed around for months. On a tenant where `smartscapeNodes ACTIVEGATE` returns 0 rows, that is "no AGs visible in Smartscape" — never proven absence — so grade fleet/health from B15 + A25 and state the version read was unavailable. The classic-API reference (`GET /platform/classic/environment-api/v2/activeGates` → `version`, `autoUpdateStatus`, `modules[].enabled`) stays unused — the 100%-dtctl design holds.
