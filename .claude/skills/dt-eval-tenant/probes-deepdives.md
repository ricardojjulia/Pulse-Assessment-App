## Deep-dive recipes (proven live 2026-07-09 — run these by default, they change reports)

**D1 — Smartscape census + agent layer.** Count nodes per type (HOST, ONEAGENT, SERVICE, PROCESS_GROUP, KUBERNETES_*, APPLICATION, DATABASE) via `smartscapeNodes <TYPE> | summarize n = count()`. ⚠️ Unknown type names return 0, not an error — absence is indicative, never proven. Then extract the agent layer (richer than B13 — full version strings, zones, host names):

```
smartscapeNodes ONEAGENT | fields name, v = dt.agent.module.version, mode = dt.agent.monitoring_mode, zone = dt.network_zone.id
```

Compare SERVICE count vs classic `dt.entity.service` — a gap = the new model is thinner than classic; note it before anyone builds segments/filters on the new surface. Smartscape `tags` = `{}` while classic entities carry tags = tagging not propagated.

**D2 — OpenPipeline stage matrix (jq over the A22 output).** Per pipeline count processors in `processing`, `metricExtraction`, `dataExtraction` (Davis events), `securityContext`, `storage`, `costAllocation`. Then cross-check **routed vs orphan**: enabled `routingEntries[].pipelineId` (A21) vs defined `objectId`s — pipelines unreferenced by any enabled route are config debt. **🔴 CORRECTED 2026-08-07 (verified live on `playground`): "unreferenced = config debt" is wrong for extension-owned pipelines.** Check each unreferenced pipeline's `externalId` FIRST — **`com.dynatrace.*`, the whole namespace and not only `.extension.`** (widened 2026-08-10), = a Dynatrace-supplied default that is not routing-table-dependent by design (live: 9 of 10 `openpipeline.metrics.pipelines` on `playground` were unrouted, and all 10 — including the one that IS routed — carried a `com.dynatrace.*` externalId; none were orphans). Only a pipeline with a `monaco:*` or **null** externalId and no route is a genuine orphan. A second live tenant carried `com.dynatrace.filesystem_filesystem-metrics`, which the narrow `.extension.` prefix misses — one object, and it would have shipped to the customer as their config debt. Killer stats: *N/14 extract no metrics* (FAQ-09 economics), *N/14 raise no Davis events*, *N routed pipelines set governance fields* (if observed record coverage exceeds what routed pipelines set → source-side enrichment dominates; say so).

**D3 — Detection enabled-split + who actually fires.** Config side: enabled vs disabled per rule set (`.value.enabled` on A2/A13) — dormant rules are latent risk and prune candidates. Fired side:

```
fetch dt.davis.problems, from:-24h | filter event.category == "CUSTOM_ALERT" | summarize n = count(), by:{event.name} | sort n desc | limit 10
fetch dt.davis.problems, from:-24h | summarize n = count(), by:{event.name} | sort n desc | limit 10
```

Join the two: which configured rules produce the noise (audit-ping detectors dressed as alerts are common), and what the *genuine* top problems are (often K8s resource pressure — cross-read B16).

**D5 — Detector rule deep-analysis (duplicates, OOTB overlap, dead inputs).** Counting detectors is not analysis — analyze every rule (local jq/python over the A2 JSON; customers with tool-migration heritage habitually create duplicates and re-implementations):

1. **Exact duplicates**: group by (normalized `query.expression`, `threshold`, `alertCondition`) — same rule, different names (`_1/_2/_3`, "(copy)"). Deletable at zero coverage cost.
2. **Near-duplicate families**: normalize titles (strip app-IDs, env/priority/test suffixes, digits) and query shapes (strip metric names/literals) → families of per-segment/per-entity clones. Each family = one generalized detector with a `by:{}` dimension.
2b. **Clone families with config drift — the highest-yield grouping (verified live 2026-07-28; groupings 1–2 both returned zero on a tenant full of them):** group enabled detectors by whitespace-normalized `query.expression` ALONE; any group whose thresholds *differ* is a clone family with drift, and the drift IS the finding (live: a byte-identical query at thresholds 80 / 3000 / 0 / 3000 — 3000 on a percentage metric can never fire, 0 with `alertCondition: ABOVE` fires permanently). Add the **threshold-plausibility check** on every enabled rule — but **classify the projected series first; the verdict turns on the metric type, never on the threshold value** (corrected 2026-07-31, v1.17.5; the earlier value-only rule false-fired on 79 of 88 flagged detectors across two live tenants). `threshold > 100` carries no information on count, duration, byte, or lag series, and `threshold == 0` + `ABOVE` is the **correct** "alert on any occurrence" idiom on count and state metrics — both are defects only on a bounded-percentage series. Also flag **self-referential expressions** (the same field on both sides of a division, e.g. `(cpu_alloc[] / cpu_alloc[]) * 100` — constant by construction, so the detector cannot vary with what it names; a silent blind spot that reads as active monitoring), and **falsify every verdict against fired volume before reporting it** — a rule called "can never fire" that produced problems, or "fires permanently" that produced 46 in a month, is a failed verdict. Full corrected recipe: `/dt-eval-prob` §3 items 4c–4e. For title families whose entity/metric names vary mid-string (which defeats grouping 2's normalization), group on the **leading token before the first ` - ` or ` : ` separator** — live, that collapsed an 80-detector per-cluster database family into 4 clean families immediately. Full recipe in the `/dt-eval-prob` skill §3.
3. **OOTB overlap**: flag rules whose title/query targets CPU/memory/disk/filesystem/availability/heartbeat/process-down — Davis detects these natively (ALERT-02: "Is OOTB Davis already detecting it? Duplicate detection means duplicate alerts").
4. **Input liveness — the killer check**: **classify each rule FIRST, then extract.** The liveness check applies **only** to detectors whose `query.expression` starts with `timeseries` (they query metric keys). Detectors built on `fetch spans|logs | … | makeTimeseries …` reference **table fields** (`duration`, `duration_ms`, …) — a naive `agg(identifier` regex extracts those as "metric keys" and then "confirms" every one absent from the metric catalogue (live 2026-07-28, a large production tenant: 3 of 8 "dead keys" in a first pass were span fields; one flagged-dead detector had fired 16× in 24 h). For the genuine `timeseries` detectors, verify each candidate key **explicitly — never by absence from a full enumeration**: `metrics from:now()-9d | filter in(metric.key, {"key1","key2",…}) | dedup {metric.key} | fields metric.key` (or per-key `filter metric.key == "<key>"` + a `timeseries` probe on one live and one dead key). ⚠️ Traps verified live: `summarize count()` over `metrics` counts ROWS/series, not distinct keys (2026-07-16, ~14k rows vs ~100 distinct keys); an unaggregated `fields metric.key` read silently truncates at dtctl's default 1,000-record cap; and **a raised cap does NOT fix it** — 2026-07-28, `--max-result-records 30000` returned 606 keys while keys provably present in the tenant were missing from the list (a targeted `filter contains(metric.key, …)` returned them). A first pass built on enumeration reported **81** detectors watching dead metrics; the per-key-verified figure was **2**. Treat "absent from an enumeration" as **unproven**, always. Syntax gotchas: `metrics` takes `from:now()-9d` with **no comma** (`metrics, from:-30d` is a PARSE_ERROR, unlike `fetch`), and metric **metadata is capped at 10 days** (`INVALID_METRICS_TIMEFRAME` beyond that) — keep the liveness window ≤ 10d. **Rules watching nonexistent metrics + `alertOnMissingData: false` = silently dead** — perceived coverage with zero real coverage. Cross-correlate with A21/A22: if the extraction pipelines are unrouted, the metrics died with them.
5. Join with fired problems (D3) to name which rules produce the noise vs which are blind.

Report shape: total → live vs dead → duplicates deletable → families generalizable → OOTB retirable → what actually fires. Sequencing warning for the report: restoring routing re-arms dead log-metric rules — prune before re-arming, and expect a tuning wave.

**D4 — Alerting delivery chain.** Three joins: davis-problem workflows' **BOTH `isDeployed` AND `trigger.eventTrigger.isActive`** (there is no top-level `isActive` field; defined ≠ delivering); `builtin:problem.notifications` grouped by `.value.type` (integration sprawl); `builtin:alerting.profile` share with `managementZone != null` (profiles chained to legacy MZs = a hard dependency the MZ→segments migration will break). One modern lane vs N classic lanes is the standard finding shape.

**D6 — OpenPipeline pipeline consolidation (duplicate/near-duplicate pipelines; VERIFIED LIVE 2026-08-07 on `playground`, dtctl 0.36.0 — see the step-0 correction below, added from that run).** D2 finds *orphans* (defined, unreferenced) and stage-coverage gaps; D6 is the missing question D2 doesn't ask — **do multiple defined pipelines run the same processing and only differ in which sources route to them?** Local jq/python over A22's pipeline objects (per scope — never merge across `logs`/`bizevents`/`events.security`/etc., A23; a pipeline in one data-type scope cannot receive another's records):

0. **🔴 MANDATORY, run before steps 1–4 — partition by ownership via `externalId` (added 2026-08-07, confirmed live: skipping this step turns platform defaults into a false consolidation finding).** `externalId` starting **`com.dynatrace.` — the whole namespace, not only `.extension.` (widened 2026-08-10 by a second live tenant, where `com.dynatrace.filesystem_filesystem-metrics` missed the narrow prefix and read as a customer-authored orphan)** — = a Dynatrace-supplied pipeline, never a customer consolidation target, whatever its processing shape or route status; report the count separately ("N extension-default pipelines, not assessed for consolidation") and stop there for that subset. `externalId` starting `monaco:*` (config-as-code) or **null** (created via the OpenPipeline app UI) = customer-authored — steps 1–4 below apply only to this subset, and a customer cannot author a `com.dynatrace.*` externalId, so the wide prefix cannot swallow real customer config. Live on `playground`: all 10 `openpipeline.metrics.pipelines` carried a `com.dynatrace.*` externalId (Cisco/Juniper/generic-SNMP/Postgres/MySQL/MariaDB/Oracle/SQL-Server/OpenTelemetry) — **zero** were consolidation candidates despite two of them (the Cisco and generic-SNMP-device reshape pipelines) sharing an identical 2-processor structure that would otherwise have matched step 1's exact-duplicate test.
1. **Exact duplicates**: two or more pipeline objects with byte-identical `processing`/`metricExtraction`/`dataExtraction`/`securityContext`/`storage`/`costAllocation` stage arrays (normalize away `objectId`/`title`/timestamps first). This is pure administrative sprawl — likely one pipeline created per source during onboarding instead of routing every source at the same existing pipeline. **Zero-risk to merge**: no processing content changes for any source.
2. **Near-duplicate families**: same processor **types and order**, differing only in literal parameters (a masking regex tuned per source, a metric-extraction field name, a DPL pattern). Normalize by stripping the literal values the way D5 strips metric names from detector queries, then group on the resulting shape. **Unlike D5's `by:{}` trick, this is NOT an automatic generalization** — a detector's `by:{}` dimension is a clean query-level mechanism; a pipeline processor has no equivalent "handle N field-name variants in one step" primitive in general. Flag the family and its literal deltas; recommend generalizing (one DPL pattern/processor covering all variants) only where the deltas are genuinely equivalent-shaped (same field semantics, different name/regex), and say explicitly when they're not (the family stays separate pipelines, tag it "same processing, source-specific parameters — not a mergeable clone"). **Worked example, verified live on `playground` (customer-authored, Monaco-managed — passes step 0):** the `cisco-asa` and `fortinet-fortigate` log pipelines are a genuine near-duplicate family — both exactly 4 `dql`-type processors in the same order (`Parse_System` → `Parse_Traffic` → `Normalize` → `Normalize_Traffic`), both normalizing to the **identical** target field set (`action`, `src_ip`, `dst_ip`, `dst_port`, `rule`, `threat_type`, `severity`, `vpn_user`, `source_vendor`, `source_product`, `hostname`, `env`, `log_family`, `site`, `event_class`, `severity_normalized`, `log_category`), differing only in the vendor-specific DPL parse pattern and field-value mapping (Cisco's `%ASA-facility-severity-msgid:` mnemonic vs Fortinet's `key="value"` pairs). This is the generalizable case: one "security-log-normalize" pipeline with a per-vendor parse stage selected by `log.source`, feeding a single shared normalize stage, would collapse two pipelines' worth of duplicated normalize logic into one.
3. **Governance drift — the highest-risk read, and the one to run before recommending ANY merge (same discipline as D5 2b, but the drift here is more consequential than a threshold):** within a candidate merge family (1 or 2 above), diff `securityContext`, `storage`, and `costAllocation` across members. **Identical processing + identical governance = the family is genuinely redundant, merge it.** Identical processing + *different* governance means the "duplicates" are deliberately separated for ABAC scoping, bucket assignment, or cost attribution — merging would silently reassign one source's security context or cost center to another's, a governance regression dressed as a simplification. Report these separately and by name: **never recommend merging a family with governance drift without first asking whether the drift is intentional design or accidental copy-paste** (the same family-shape can be either, and only the owner knows which).
4. **Orphan cross-check (reuse D2's corrected version, extend it): a pipeline is unreferenced only if it's missing from BOTH consumer surfaces** — A21's enabled `routingEntries[].pipelineId` **and** A22's pipeline-**group** membership (D2 already warned pipeline groups may legitimately hold 0 objects, but where they don't, a pipeline referenced only via a group and never a direct route is not orphaned) — **and only after step 0 has already excluded extension-owned pipelines from this check**. True double-negative orphans in the customer-authored subset are the cheapest, zero-ambiguity win: delete outright, no family analysis needed.
5. **Volume-weight the canonical choice**: before naming which family member survives a merge, pull each member's observed record share (B45 per-source volume where the pipeline dimension is resolvable, else B1's routing/default-bucket split as a proxy) and keep the **highest-volume** member as canonical — repointing the low-volume routing entries onto an established, already-proven pipeline is lower-risk than repointing high-volume traffic onto a rarely-used one.

**The consolidation mechanic itself is simpler than D5's** — no new config needs to be authored. For an exact-duplicate or safely-generalized family: (a) name the canonical survivor `pipelineId`, (b) list every routing-entry `objectId` (A21) currently targeting a non-canonical member, with the edit being "repoint `pipelineId` → `<canonical>`", (c) after repointing, confirm zero remaining routing-entry or pipeline-group references to each non-canonical member (step 4's orphan check, re-run), then delete it. Emit this as a worklist mirroring D5's CSV shape: `family_id, member_pipelineIds, canonical_pipelineId, member_record_share, governance_drift (y/n + which field), disposition (merge / keep-separate:<governance reason> / delete-orphan), routingEntries_to_repoint`.

Report shape: total pipelines → orphans deleted → exact-duplicate families merged → near-duplicate families generalized-or-kept-separate (name which and why) → governance-drift families flagged, never auto-merged. Cost: A21/A22 reads are the cheap settings objects already collected; the volume-weighting join reuses B45/B1, both already inside the standard guardrails.
