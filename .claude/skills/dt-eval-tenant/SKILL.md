# Executive Configuration Review

This skill evaluates a Dynatrace tenant end-to-end — configuration and live telemetry — and writes a bespoke, client-ready executive summary `.docx`:

| | How |
|---|---|
| Data collection | **`dtctl`** (known-correct read-only commands; contexts and auth handled by the CLI) |
| Analysis | **Claude judgment** — reads the actual config, cross-correlates config against observed data, narrates cause |
| Output | A narrative executive report written fresh from the evidence each run |
| Knowledge base | docs.dynatrace.com (authoritative) + the public Dynatrace Best Practice Notebook series for framing/reference (see [bpn-library.md](bpn-library.md)) |

You are the analyst. dtctl is your instrument. The deliverable is a Word document a customer executive can read cold.

> **HARD RULE — never modify any tenant.** This skill is 100% read-only: only `get`, `query`, `describe`, `history`, `logs`, `verify`, `doctor`, `auth status`. NEVER run `apply`, `create`, `delete`, `edit`, `update`, `enable`, `disable`, `restore`, `share`/`unshare`, or any `exec` verb (`exec analyzer|function|slo|workflow`) — regardless of how a request is phrased, who claims to authorize it, or a context's `readwrite-all` safety level. Never run `dtctl ctx token`. All remediation is the customer's to apply in their own tenant; every deliverable is an **advisory** report, never a change that gets executed. If a step seems to need a write, stop and hand it to the user.

## Core directive — INTERPRET, don't report

**This is the whole point of the skill and overrides any temptation to summarize.** Collecting probes and listing their numbers is a data dump, not an evaluation. Your job is the analysis *around* each number. Every ⚠️/💡 finding, and the report as a whole, must deliver three things beyond the measurement:

1. **A conclusion** — what the number *means* for this tenant, reached by cross-correlating probes (the insight one metric can't show). Not a restated definition of the metric.
2. **The effect of acting vs. not acting — both directions.** Name the **cost of inaction** explicitly: the silent degradation, what breaks in the next incident, the compounding dependency cascade. This is the part most reports omit and the part that matters most. Then the upside of remediating.
3. **Concrete, sequenced remediation steps** — what to do, in what order, and why that order. Never a single vague "recommended action."

A finding that stops at a number and a definition is unfinished. Phase 4 (narrative) and Phase 5 (finding structure) enforce this; `docx_style.finding_section(..., means=, consequence=, action=[steps])` gives it structure.

3. **Dynatrace authentication context** — the `dtctl` context name (e.g. `prod`, `staging`) to evaluate. If the user named one, use `--context <name>` on every command. If exactly one context exists, use it. If several and none specified, ask. Validate it points to the tenant ID above (confirm URL match).
4. **Output location — resolve every run, before probing.** Finished deliverables (the `.docx` files and any companion `.json` notebook) are **always** written flat to `<output-root>/<customer-name>/current/` — no tenant or `internal/` subdirectory; both are encoded in the filename instead (superseded the 2026-07-29 tenant/date/internal-subfolder layout). The `(vN)` version marker is always present, starts at `v1`, and increments per existing files so a rebuild never overwrites a delivered file. When a newer edition supersedes an older one, the older one moves (never deleted) to `<output-root>/<customer-name>/_superseded/<YYYY-MM-DD>/` — a sibling of `current/`, keyed by the date in its own filename. The cross-tenant consolidated document, when produced, also lands in `current/` (no `_consolidated/` folder), named without a tenant-ID prefix since it spans more than one tenant. Resolve `<output-root>` in this order: (a) the `DT_EVAL_OUTPUT_DIR` environment variable if set — it wins and suppresses any prompt (headless/cron); else (b) the default in [output-config.json](../.dt-eval-common/output-config.json) (`default_output_root`, currently `~/Documents/Dynatrace-Reviews`), applying that file's `prompt_mode` — `always` = confirm the location at the start of every run pre-filled with the default (one keystroke to accept, or type a path to override *for this run only*, which never rewrites the stored default); `on-request` = use the default silently and prompt only when the user asks; `never` = use the default with no prompt. **Session scope:** in a multi-skill engagement (several `/dt-eval-*` invocations in one session, same tenant/customer), the root confirmed by the first skill is **inherited by sibling invocations without re-prompting** — re-confirm only when the tenant/customer changes or the user redirects it. Expand a leading `~` to the user's home and create `<root>/<customer-name>/current/` before writing. **This governs deliverables only** — run-state (`runs/…`) still lives in the skill repo per the run-state protocol, and the intermediate gauge PNG still goes to the scratchpad, never beside the deliverables.

   **Tenant layout — ask ONCE per customer, only when there is more than one tenant** (owner decision 2026-08-27). A customer with several tenants may keep every tenant's deliverables side by side in one `current/` folder (**flat**, the default and the existing behaviour), or give each tenant its own subtree (**per-tenant**, `<output-root>/<customer-name>/<tenantId>/current/` with its own `_superseded/` sibling). Run `.venv/bin/python ../.dt-eval-common/layout.py status --customer "<name>" --tenant <tenantId>` at Phase 0; when it reports **MULTI-TENANT, LAYOUT NOT CHOSEN**, ask the user (AskUserQuestion) which they want, pre-filled with *flat*, then record it with `layout.py set --customer "<name>" --layout <choice>` — which also **migrates what is already on disk** (files move, never deleted; a superseded edition stays superseded; a cross-tenant document stays at the customer level). A **single-tenant** customer is never asked and never nests. The answer is stored in `<output-root>/<customer-name>/.dt-eval-layout.json` and **every sibling skill inherits it without asking again** — the layout belongs to the customer, not to a run, because half a customer's reports nested and half flat is two live editions of one report in two folders, which is exactly what `current/` exists to prevent. `DT_EVAL_TENANT_LAYOUT` overrides and suppresses the prompt for headless runs. If `layout.py status` reports deliverables it could not attribute, pass the missing ids with `--tenant <id>` (repeatable) rather than letting them stay behind.
5. **Deliverables — ask immediately, before any probing, every run.** Present a single checklist (pick one or more):

Answer it by ticking **Summary** alone in the checklist above — and understand what the option does *not* mean: **a reduced deliverable set never reduces what gets collected.** Phases 1 and 2 run the complete probe battery exactly as they would for all three documents. The INTERNAL REPORT is always graded, and the Summary is score-free by mandate either way. See [report-audiences.md](../.dt-eval-common/report-audiences.md) § *Grades are an option*.

## Run state — one durable file per run (append, resume, compare, report)

Every run lives in **`runs/<tenantId>-<YYYY-MM-DD>/`** in the repo (NOT the scratchpad — it must survive the session for future comparisons): raw probe outputs as files (`01-buckets.json`, …) plus **`run.json`**, the accumulating run-state file managed by [runlog.py](../.dt-eval-common/runlog.py) (stdlib-only; run with `.venv/bin/python` or any python3). **Run `runlog.py` from this skill's own directory** (`.claude/skills/dt-eval-tenant/`) — every `runs/...` path below is relative to cwd, not to the script's location, and `runlog.py` now refuses a relative run path that would resolve outside a skill's own `runs/` dir (invoking it from the repo root once silently wrote `runs/<id>/` at the repo root, invisible to `runlog.py find`'s cross-skill cache lookup — live 2026-08-05, a pair of same-day reference-tenant runs). **Date-parse rule — tenant IDs are often hyphenated** (`afi-prod`, `corp-ag`): the run date is the **trailing `YYYY-MM-DD`** of the directory name — parse with `basename[-10:]` or `rsplit("-", 3)`, never `split("-", 1)` (which yields `prod-2026-07-28` and crashes strptime; `report_builder.ReportMetadata.run_date` already uses the rsplit form).

**Protocol — follow it strictly:**

1. **Start (Phase 0):** `runlog.py init runs/<id>/run.json --tenant <id> --url <https://id.apps.dynatrace.com> --context <name> --customer "<customer-name>" --requested-by <email>`, where `<email>` comes from running `dtctl auth whoami` first (omit the flag only if whoami is unavailable, e.g. a platform-token context) — the shared `build_reports.py` scaffold reads it back from `run.json` at build time and names this user on every cover's AI-disclosure footnote, so it only needs capturing once, here. **Check the clock before reusing a "same-day" run dir** — if the session has crossed midnight since the earlier invocation, this is a NEW day's run: roll forward with **`runlog.py roll runs/<tenantId>-<old-date>/run.json runs/<tenantId>-<today>/run.json`** — it copies the raw evidence, carries every probe record forward with `carried_forward_from` provenance, stamps `meta.collection_span` (the "collected July 15–16" the method note states), and never touches the prior run (that run.json is the diff target for future engagements — bitten live 2026-07-16, improvised painfully again 2026-07-28/29; never hand-roll the roll-forward). If it prints `EXISTS (in progress)` you are **resuming**: 
   - **Cache age check:** parse the timestamp from `run.json` and calculate age. **Default behavior: reuse existing cache** unless:
     - Cache is **over 24 hours old**, OR
     - User explicitly passed a `--fresh` flag when invoking the skill.
   - **If cache is over 24 hours old**, prompt: *"Cached data is X hours old. Use it anyway, or refresh probes?"* (AskUserQuestion; default `yes` — reuse; `no` — refresh).
   - **If refreshing** (user chose `no` OR `--fresh` flag): run `runlog.py status run.json --expected <full probe list>` — the canonical full list is **A1–A54 + A4b (§A) and B1–B50 + B4b/B39b/B40b (§B)** per the probes-\*.md catalog (keep this range current when probes are added — a stale expected list silently inherits retired footnote text instead of flagging the new probe `missing`, which is how a delivered appendix once carried the retired ActiveGate "not assessed" wording after B36 shipped); skip everything `ok`/`unknown`, rerun `error`, run `missing`, then refresh each affected probe's record.
   - **If reusing** (default or user chose `yes`): skip collection, proceed directly to Phase 1 analysis.
   - Either way, **documents are always recreated new** — reuse applies to probe data only, never to a previously built docx (input #6).
2. **After every probe** (as you move down the list, not in a batch at the end): save the raw output to a file in the run dir, then
   `runlog.py record run.json <probe_id> ok --summary '<compact JSON of the numbers you will cite>' --raw <file>`
   — `unknown` for 403/⚪ (with `--note` naming the missing scope), `error` for failures worth retrying. The summary is the contract: every figure the report cites should appear in some probe's summary, so the report can be rebuilt (and compared) from `run.json` alone. **zsh trap:** never alias the interpreter+script as a scalar — `RL="python3 …/runlog.py"; $RL record …` fails (`no such file or directory`) because zsh does not word-split unquoted variables (the same trap field-notes.md documents for dtctl flags); a batch of record calls lost this way inside an `&&` chain looks successful while recording nothing. Use the **array form** — `RL=(.venv/bin/python .claude/skills/.dt-eval-common/runlog.py)` then `"${RL[@]}" record …` — or write the full command each time.
3. **Compare (Phase 4):** find the most recent *completed* prior run for the same tenant (`ls runs/`, check `meta.completed`) — **and independently glob the output directory** (`<output-root>/<customer-name>/current/` for `<tenantId>-*.docx` and `[INTERNAL ONLY]-<tenantId>-*.docx` — the current convention — plus the legacy layouts: `<output-root>/<customer-name>/<tenantId>/*/` plus `*/internal/` (the 2026-07-29 tenant/internal-subfolder convention), `*/external/` (2026-07-29 morning audience-subfolder convention), `<output-root>/<customer-name>/*/` with `<tenantId>-*.docx` filenames (2026-07-28 dated-subfolder convention) and the flat `<output-root>/<customer-name>/` (pre-2026-07-28), **plus any `_superseded/` folders** (now a sibling of `current/`, keyed by date, rather than nested under a date folder) where re-organized older deliverables may have been moved; reconcile by **tenant ID in the filename**, never by stored path — a prior run's `run.json` `report.path` is a historical record of where the file was written, not a live pointer, and files move after delivery), because the two diverge (a refresh, another machine, or cleanup empties `runs/` while delivered reports still exist — live 2026-07-28: Phase 0 said "no prior runs" while the output folder held two delivered reports from that same week, exactly the silent-"first review" failure rule 2b exists to prevent). Prior *deliverables* found without run state still count as "a prior review exists" for rule 2b. **If prior runs OR prior deliverables exist, ASK the user before building the report** (AskUserQuestion): *use the previous run(s) for comparison, or treat this as a fresh report?* — and if comparing, *was the prior report delivered to the client?* (Comparison content may appear in the deliverable only when the prior report was delivered — see report structure 2b.) Always run `runlog.py compare` for the user's own view regardless of the answer. **`runlog.py delivered <tenantId>` performs the current-convention half of the output-directory glob for you** — it returns the delivery dates found under `<output-root>/<customer>/current/` by matching the tenant ID against every filename there (both audiences), and `runlog.py find` prints the "reports exist with no run state" warning itself when it comes up empty. Still glob by hand for the **legacy** layouts listed above; the command does not know them.
4. **Finalize (Phase 5):** the docx build script reads its numbers from `run.json` summaries (raw files for detail). After the report(s) save and verify, call `runlog.py finalize` with:
   - **Configuration Review:** `runlog.py finalize run.json --skill tenant --overall <n> --grade <G> --confidence <High|Medium|Low> --pillars '<json>' --report <path> --audience external|internal`. **Always pass `--skill`** — it namespaces the result under `results.tenant` so a sibling skill finalizing the same run directory later the same day cannot clobber this skill's recorded score (the flat `scores`/`report` keys are a most-recent alias only; a live prob finalize once overwrote the config review's score and the pillar decomposition was unrecoverable). **Always pass `--confidence`** too — it and `--skill` are what let `finalize` synthesize the cross-skill `headline` block (`run.json`'s `headline` key) that the `dt-eval-rollup` skill reads; the confidence value is whatever `score_checks()` already returned for this run (§ scoring mechanics below), not a new computation. **Finalize once per edition** — when a run produces both the customer-facing and the `[INTERNAL ONLY]-` document, call finalize for each; both are kept under `run.json`'s `reports.configuration_review.{external,internal}`, whereas the flat `report` slot holds only the most recent (before that block existed the second call erased the first edition's path outright).
   - **finalize refuses a run with unrecorded evidence:** it scans the run directory for raw files no probe record references and fails, listing the orphans, unless `--force` is passed. Record the orphans first (`record … --raw <file>`) — a run finalized with collected-but-unrecorded evidence cannot be rebuilt or compared from `run.json` alone (a field run once finalized 238 raw files with only 61 recorded probes).

Interrupted runs resume from step 1 at no re-collection cost; completed runs become the baseline the next engagement diffs against.

### Concurrency — parallel runs for different tenants

**Multiple instances are safe to run concurrently FOR DIFFERENT TENANTS.** Each tenant has its own run directory (`runs/<tenantId-A>-<date>/`, `runs/<tenantId-B>-<date>/`, …), so there is no locking conflict.

**For the SAME tenant on the SAME day**, locking prevents collision:

- **init** automatically acquires a directory-level lock (`runs/<tenantId>-<date>/run.lock`). If another instance holds the lock:
  - **Default behavior (no flag):** Error immediately with a clear message
  - **`--wait` flag:** Block and poll every 2 seconds until the lock is released (1-hour timeout). The wait re-checks staleness on each poll, so a holder that dies rather than exiting cleanly is detected in seconds instead of running out the full hour.
  - Example: `runlog.py init runs/abc-2026-07-28/run.json --tenant abc ... --wait` will wait for an in-progress run to complete.
- **finalize** automatically releases the lock when the run completes.
- **A lock whose holder is gone is cleared automatically (2026-08-24).** `finalize` is what releases a lock, so a run killed partway through — crash, interrupt, closed terminal — leaves one behind, and only a same-tenant, same-day run ever trips over it (found in the field 20 days after the fact for exactly that reason). `init` and `lock` now read the holder recorded in the lock (`<ISO timestamp> <pid> <hostname>`) and clear it **only** when that process is provably gone on this host, printing `STALE LOCK cleared: …`. Every other case fails CLOSED and still refuses: a live holder, a lock from another machine (a pid there says nothing about a process here), a pid that cannot be probed, or a malformed/legacy lock with no pid. The asymmetry is deliberate — breaking a live lock puts two writers in one run directory, whereas refusing to break a dead one costs one `unlock`. **Parsing note if you ever read a lock by hand: the pid is field 2. The first number on the line is the year**, so a regex for the first integer returns `2026` — which is a plausible pid, so the wrong process gets probed and the verdict is accidental.
- Manual **lock/unlock** commands are available for explicit control if needed (rare):
  - `runlog.py lock runs/abc-2026-07-28/run.json [--wait]`
  - `runlog.py unlock runs/abc-2026-07-28/run.json` — the deliberate override when a lock is held or unverifiable and you have confirmed no other run is writing there.

**Recommendation:** For your use case (different tenants in parallel), no action needed — concurrency is automatic and safe. If you ever need to run multiple evaluations of the same tenant same-day, pass `--wait` on the second instance's init call.

**The OUTPUT directory needs its own discipline — the run-dir lock does not protect it.** Concurrent runs for different tenants of the same customer once shared one folder, and that collision destroyed completed deliverables twice on 2026-07-28 (each session's "clean up the old v1" glob deleted the *other* session's finished files). Every customer's tenants now share one flat `<customer>/current/` folder again (the tenant subtree was eliminated once the tenant ID moved into the filename), but the collision is still structurally impossible — **the leading `<tenantId>-` token in every filename means two tenants can never share a stem, and the atomic `(vN)` reservation (O_EXCL) means two concurrent builds of the SAME tenant can never claim the same version** — but two rules remain mandatory:

1. **Never glob-delete (or delete at all) in the output directory.** Rebuilds increment `(vN)`; they never clean up. Version churn is cheap; a deleted deliverable is unrecoverable. If the user wants old versions gone, that is their action, not the skill's.
2. **Verify by re-stat, not by save-success.** A printed save path proves nothing 90 seconds later. The final report to the user must re-stat every deliverable from disk immediately before reporting the paths (the shared `build_reports.py` scaffold does this; a hand-written build script must too).

**Auth modes — both work for every dtctl command in this skill.** A context is backed either by a **platform token** (`dtctl config set-credentials`) or by **browser-based SSO OAuth** (`dtctl auth login --context <ctx> --environment https://<tenant>.apps.dynatrace.com`) with automatic token refresh. Prefer OAuth when setting up a new engagement: no long-lived secret on disk, refresh keeps a long evaluation alive, and `dtctl auth whoami` gives the auditor attribution for the report's method note. If `auth status` shows an expired OAuth session, ask the user to run `dtctl auth login` (it opens their browser — an interactive human step; wait for them, don't work around it). On headless systems the user needs `DTCTL_TOKEN_STORAGE=file`. The user's IAM permissions bound what an OAuth session can read — shortfalls surface as 403s and follow the normal ⚪ rule.

Then map the token's reach **before** probing: run the key Phase-1/2 commands with the global `--check-scopes` flag (predicts the required-scope check without executing) to pre-declare which areas will be ⚪ — better than discovering 403s mid-run. `dtctl token-scopes` prints the scope reference per safety level if the user asks what to grant.

**Then map what data exists** with `dtctl inventory` (≥ 0.35; read-only, budgeted DQL battery — nothing persisted server-side). Where `--check-scopes` answers *"may I read it?"*, `inventory` answers *"is there anything there?"*: fetchable vs query-only data objects, buckets + segments, the live entity-type census, and capabilities (spans, logs, RUM, k8s, cloud integrations, metric families, …) reported present/absent/**unknown** — with the evidence cited for every absent capability. Save the output to the run directory as `00-inventory.json` and use it two ways: (1) fold scope denials into the ⚪ pre-declaration alongside `--check-scopes`; (2) when a capability is **absent with evidence** (e.g. no RUM data objects populated), annotate that probe family up front from the cited evidence rather than discovering empty results probe by probe — then spot-confirm with the family's cheapest probe, since the inventory is a preflight signal, not a replacement for §A/§B evidence. Rules: `unknown` means could-not-check (failed probe or exhausted budget) — treat as ⚪, **never** as absent; **`absent` is entity-census-scoped** — it means no *entities* of that type are modelled, while metric *dimensions* from the same cloud/platform may still be fully populated via extensions (never infer dimension absence from entity absence — test the actual dimension, e.g. a segment's `variables` DQL per A6, before calling it dead; a live 2026-07-28 report drew exactly that wrong inference and had to be rebuilt); keep `--scan-limit-gbytes` at 5 on large tenants (the dtctl default is 25 GB per discovery probe — over cost guardrails for this tenant class); and in client deliverables an absence stays "not observed in this environment" — the inventory evidence is for your working notes, never quoted as internal machinery.

All commands in this skill are **read-only** (`get`, `query`, `describe`, `history`, `logs`, `verify`, `inventory`). Never run `apply`, `create`, `delete`, `edit`, `update`, `enable`, `restore`, `share`/`unshare`, or any `exec` verb (`exec analyzer|function|slo|workflow` execute things on the tenant). **Never run `dtctl ctx token`** — it prints the resolved credential, and since the evaluation is 100% dtctl (no curl), nothing needs it. If `doctor` reports auth problems, stop and tell the user — do not attempt to mint or edit credentials.

## Phase 4 — Analysis

### Scoring (same rubric as the rest of the repo)

- Per check: ✅ Healthy = 100, 💡 Opportunity = 50, ⚠️ Needs attention = 0, ⚪ Unknown = **excluded from the denominator** (a token gap must never read as a config gap).
- Pillar = weighted mean of assessable checks; overall = weighted mean of assessable pillars. Grade bands: A ≥ 85, B ≥ 70, C ≥ 50, D < 50. **Compute with `scoring_engine.score_checks()` — the one shared implementation of this rubric** (it handles the ⚪ reweighting, returns grade + confidence, and accepts statuses for pillars and numeric pillar values for the overall). Hand-rolled arithmetic is how skills silently drift apart on the ⚪-exclusion rule; `/dt-eval-prob` areas and `/dt-eval-gen3` domains use the same call.
- **Effective Consumption & Gen3 Migration Progress** — these are separate, standalone skills (`/dt-eval-consumption` and `/dt-eval-gen3`). Do not score either as a pillar within dt-eval-tenant Configuration Review; invoke each skill independently when needed (they ask their own Phase 0 inputs and produce their own `.docx` and optional `.json` outputs). See their respective SKILL.md files for scoring details.
- **Cross-cutting scoring mechanics (upgraded 2026-07-14, full mechanics in [effective-consumption.md](effective-consumption.md)):** (a) **outlier guard** — fence per-actor counts at `median + 3×IQR` before any distribution KPI or hotspot list; fenced actors are named, leave the human math, and join the automation story; (b) **confidence flags** — every pillar score carries High/Medium/Low (denominators ≥100 / 30–100 / <30 or majority ⚪); the final flag is the **minimum** of the sample-size band and the ⚪ band — pass the underlying sample sizes via `score_checks(..., denominators={...})` so the rubric is computed, not asserted (a 2-check area resolved cleanly is not High-confidence evidence; without denominators the function can only apply the ⚪ band); a Low flag must be stated wherever the score appears; (c) **trend classification** — chronic (below target every week: *activate*, not *restore*) vs regression (≥15-point in-window drop: urgent, what changed?) vs improving (credit it); never narrate a weekly move on a bin under 30 events/users/problems; (d) **EUB is context, never an OES input** — the expected-users comparison is an estimate and is always labeled as one.
- **Gen3-first (user rule, 2026-07-09): never score the absence of a Gen2/classic construct as a gap** — that turns the report into a legacy shopping list. Classic problem notifications, alerting profiles, auto-tagging rules, management zones, and ownership-team objects are collected as *inventory*: their **presence** signals migration debt (MZ2POL etc.); their **absence is clean**. Score the *outcome capability* on its platform-native mechanism instead: alert delivery → davis-problem **workflows** (coverage/filters); scoping → **segments**; tagging/ownership → **source tags** (deployment config, K8s labels, cloud tags) and pipeline enrichment; access → `dt.security_context` + IAM policies. A tenant with 0 MZs, 0 classic notifications, and workflow-based delivery is in the *target* state — say so. Recommended actions must never instruct the client to create classic constructs.

### Narrative (what makes this flavor worth running)

**INTERPRET, don't report (owner directive — the whole point of this flavor).** A measured number is *evidence, not a conclusion*. Reporting "static detectors: 22/26" is a data dump; the job is the analysis that follows — what it *means*, what it *costs to leave alone*, and *how to fix it*. Every ⚠️/💡 finding must carry all three: (a) a **conclusion** drawn by cross-correlating probes (the insight one metric can't show); (b) the **effect of acting vs. not acting — both directions**, and the do-nothing consequence is the part most reports omit and the one that matters most: the silent degradation, what breaks in the next incident, the compounding cost; (c) **concrete, sequenced remediation steps**, not a single vague "recommended action." If a finding is just a number and a restated definition, it is not finished.

Write the analysis as a tenant evaluation an executive can read cold — measured value, what it means, what happens if ignored, what to do — and frame the "why it matters" through FAQ-12 (partial-enablement handicaps):

1. **Cross-correlate before concluding.** The interesting findings live *between* probes: routing works in one place but not another; topology depth is good but confined to the Full-Stack minority; alert volume is high *because* the detector config is all static thresholds. State those causal links explicitly — they ARE the conclusions.
2. **Habit → gap → handicap.** For each major gap, name the likely operating habit it came from ("ported threshold alerts", "logs live in the log tool"), what it leaves off, and the *silent* degradation — what stops working that nobody will notice until an incident (FAQ-12 §4 is the template).
3. **The dependency cascade (FAQ-12 — now measurable end-to-end, not just asserted).** Where Full-Stack coverage, logs, RUM, or AppSec are partial, explain the compounding cost: each withheld layer degrades Davis, topology, and every layer above it — partial adoption re-creates the separated tools the customer just paid to leave. **Build the cascade from the measured rungs** rather than restating it as theory: code modules → traces (B17: spans present? OTel/OneAgent split) → services + topology (B7/D1) → Davis RCA (B28 signal-to-problem compression, B4) → AppSec (B26/B27: is `security.events` dark on Full-Stack hosts?) and RUM (B22/B23: sessions/CWV present?), with logs (B1/B12) as the evidence layer. When a rung is thin, name what it silently removes from every rung above it. **Call out FAQ-12's two traps explicitly whenever the data shows them — they are the sharpest cost-of-inaction arguments:** (a) the **AppSec context trap** (corrected 2026-07-29 against the AppSec docs — the old "cannot be switched on later without re-basing coverage / silently foreclosed runtime security" claim overstated the docs and must not be asserted): per docs.dynatrace.com Application Security, third-party and code-level vulnerability detection run *Full* in Full-Stack and *Limited* in Infrastructure/Discovery, and Runtime Application Protection runs *Full* in all three — what Infrastructure/Discovery **lose is environmental context** (reachable data assets, public-internet exposure), so the Davis Security Score cannot adapt to topology and risk stays at raw CVSS base scores. The defensible finding: *enabling AppSec ahead of Full-Stack coverage produces an unrankable findings queue, because the triage intersection (exposure ∧ exploit ∧ function-in-use) that B26 depends on is exactly what Infrastructure mode cannot populate.* Verify the capability matrix against the current docs each run and cite the page; (b) the **history trap** — RUM baselines, experience SLOs, and Davis user-impact history begin accruing only at enablement, so "we'll add it when we need it" guarantees no history precisely when it's needed. Both are grounded in docs (monitoring modes; AppSec monitoring modes) — verify and cite.
4. **Evidence discipline.** Every figure cited must come from an evidence file. Extrapolations (day-rates from 2-minute samples) must be labeled *derived*. Qualitative reads (naming-scheme quality) must be labeled as such. ⚪ rows are "gaps in the audit token's reach, not confirmed passes."
5. **Actionable, sequenced.** Each finding ends in a concrete next step; the plan section sequences them (fix routing before retention tiers; Full-Stack before AppSec; enrichment before ownership routing).

### Ground every recommendation — docs.dynatrace.com is authoritative, BPN is the reference layer

Three-level authority hierarchy, applied to every ⚠️/💡 finding:

1. **What is true in this tenant** → the measured evidence (probes). Nothing overrides a measurement.
2. **What Dynatrace recommends** → **docs.dynatrace.com is the authoritative source.** Verify each recommended action against the current official documentation before it goes in the report, and cite the doc page (title + URL). Shortcut: the BPN notebooks' *Sources* footers already link the exact doc pages per topic — pull those URLs and WebFetch them rather than searching from scratch.
3. **Why it matters / how to explain it** → the **BPN library** ([bpn-library.md](bpn-library.md): path, finding-area → series mapping, citation rules). Use it for the habit → gap → handicap framing, worked DQL, migration context, and sequencing — and cite series entries as *further reference*, never as the authority for a recommendation.

Conflict rules: docs beat notebooks (note the discrepancy); measurements beat both for statements about the tenant's state. If you hold customer-specific engagement material locally (prior assessments, design reviews), read it **before** analyzing — the report must be consistent with prior engagement findings — but never cite it by name (see hygiene rules below). ## Phase 5 — Write the Word document

Write a Python build script in the scratchpad that imports the house-style helpers from [docx_style.py](../.dt-eval-common/docx_style.py) (run with the repo venv `.venv/bin/python` — created by `setup.sh` — **or any python3 with python-docx installed**: installed skill copies have no venv and no setup.sh, so check the interpreter has `python-docx` — plus optional `Pillow` — *before* the build step, and fail loudly there rather than at report-build time). Parse every dtctl JSON you read with the shared lenient loader ([dt_json.py](../.dt-eval-common/dt_json.py) — `load_dtctl_json`/`load_dtctl_file`/`rows()`): it clears both known invalid-JSON modes, unwraps the `{ok, result, context}` envelope, and normalizes the two zero-row shapes (`result: null`, records-absent) that break naive `len()` — see field-notes. **The run date is pinned once, at Phase 0, when the run directory is created** — every later consumer (output filename, cover date, method/collection notes, and especially the build script's `run.json` path) takes the date **from the run directory name, never by re-deriving `date.today()`** — a session that crosses midnight otherwise mis-dates the deliverable and points the build at a nonexistent run dir (bitten live 2026-07-15→16). Never hardcode a date literal either; read it from the run dir. **The filename always carries the COLLECTION date — the run-directory date — never the build date** (build time is irrelevant to the reader, and a build that merely crosses midnight must not re-date the deliverable). When collection itself genuinely spans two days (a refresh finishing after midnight), the method note states the span ("collected July 15–16") while the filename still carries the run-directory date. The helpers give you the cover page, grade colors, scorecard/status tables, callout boxes, and **dynamic visual summaries** (see below); **the narrative prose is yours to write per run** — never paste boilerplate findings. The shared [build_reports.py](../.dt-eval-common/build_reports.py) is a **structure-only scaffold** enforcing exactly that: it takes a per-run findings module (scratchpad-only — it holds tenant data) supplying every number and sentence, and **raises on any missing or empty field**. It contains no content of its own and must stay that way — a hardcoded example finding in a shared builder is a fabricated-evidence generator waiting to ship another tenant's numbers.

**Visual result summaries (help the executive *see* the results, not just read them).** All are driven by the run's actual scores and use the report palette:
- `render_gauge_png(overall, path)` → a semicircular score dial (colored A/B/C/D arcs + needle), embedded on the cover via `cover_page(..., gauge_path=...)`. **Optional — needs Pillow**; returns `None` when Pillow is absent, and `cover_page` then falls back to the colored text grade badge automatically (no crash, no manual check needed). Write the gauge PNG to the **scratchpad** (a temp path) — it is embedded into the `.docx`, so it is an intermediate, not a deliverable; do **not** leave it in `<output-root>/<customer-name>/current/` beside the report (that folder should hold only the `.docx` files and, when EC is on, the companion notebook).
- `pillar_bar_chart(doc, {pillar: score|None})` — native (zero-dep) horizontal bar chart, bars colored by grade band, ordered worst-first; the single clearest picture of where the estate is strong vs. weak. Put it with the **Scorecard** (structure item 4). `None` scores render as ⚪ N/A rows (do not fabricate a number).
- `rag_summary(doc, healthy, opportunity, attention)` — proportional ✅/💡/⚠️ stacked bar (⚪ excluded, per the hard rules). Put it in the executive summary or beside the scorecard.
These are **not** a substitute for the INTERPRET narrative — they orient the reader; the deep-dives still carry the conclusion/consequence/action. Keep visuals to results the reader must grasp fast (overall grade, pillar shape, status mix); don't chart raw probe counts (vanity).

**Content structure by deliverable type ([report-audiences.md](../.dt-eval-common/report-audiences.md) is the full reference):**

- **INTERNAL REPORT:** scoring-derivation table (pillar | weight | score | contribution, noise-penalty line, Foundation-gate status, outlier-guard notes) directly after the scorecard; **Talk-track & expansion hooks** block closing every pillar/deep-dive section (hook rules in report-audiences.md — only non-nirvana capabilities from [rate-card.md](rate-card.md), one hook per sequenced fix, never a dollar quote); the **consolidated talk-track & expansion matrix** before the action plan; the **rate-card consumption-depth table** (⚪-footnoted if `dt.billing.*` is unreadable); per-pillar **confidence flags**; and the **⚪ input roster** with verbatim asks. Internal voice per report-audiences.md; cover subtitle *"Dynatrace internal — not for customer distribution"*; filename carries `-internal`.

- **Summary (customer facing):** qualitative only (no scores, grades, or metrics). Narrative of strengths, opportunities, and suggested first steps. Fully self-contained; full hygiene rules (no internal machinery, no cross-tenant references).

- **Detailed (customer facing):** full scorecard with pillar breakdowns and numbered findings. Same math as Internal report, customer-appropriate voice with full hygiene rules applied (no run-state mechanics, no internal references, no cross-tenant comparisons).

Document structure:

1. **Cover** — "Dynatrace Technical Configuration Review", customer, tenant URL, date, and the overall score + grade **on the editions entitled to one** (use `cover_page()`); render the score **gauge** with `render_gauge_png()` and pass it as `gauge_path` (falls back to the text badge if Pillow is absent). **Grades are an option on a customer-facing edition and off unless this run asked** (input #5): pass the computed score and grade to `cover_page()` exactly as they are and let it decide — it suppresses score, grade and gauge together via `grades_enabled(internal, grades)`, so a hand-written build script gets the rule for free and only has to forward its own `grades=` flag. `cover_page()` automatically adds the **AI-disclosure footnote** at the foot of the cover (AI-generated evaluation, read-only data within the access scope granted to the requesting user, expanded permissions may surface more) — pass the authenticated Dynatrace user's email from `dtctl auth whoami` as `requested_by=` so the notice names whose scope bounded the review (omit it only if whoami is unavailable, e.g. a platform-token context). Leave the footnote in place for every audience; don't suppress or reword it per run. **When building through the shared `build_reports.py` scaffold, this is already handled** — `_add_cover` defaults `requested_by` from `run.json`'s `meta.requested_by`, captured once at Phase 0 (`runlog.py init --requested-by`); only a hand-written build script calling `cover_page()` directly needs to pass it explicitly.
2. **Executive Summary** (~1 page, prose, no field names or DQL): the verdict sentence, 3–5 headline findings each tied to business impact, and the one-paragraph "what to do first".
2b. **Changes since last review** — include ONLY when the prior run's report was itself **delivered to the client** (user rule, 2026-07-09). A comparison section reveals that prior measurements exist; if the client never received that review, the section outs internal work. First delivered report on a tenant = **no comparison section**, no "baseline" language, no references to earlier internal measurements or sibling-tenant validations not performed in this review. Facts observed *within* this review's own window may be stated as such ("grew by 38 within the two-day review window") — the method section's collection dates must cover the window claimed. The `runlog.py compare` output still runs every time — for you and the user, not the client — and becomes a report section only from the second *delivered* review onward.
3. **How to read this report** (short): status legend is ✅/💡/⚠️ **only** — plus one sentence: items that could not be assessed (typically permissions) are excluded from every score and listed as appendix footnotes.
4. **Scorecard** — one table: Area | Measured | Status | Recommended action (use `scorecard_table()`; **rows are DICTS with keys `area`/`measured`/`status`/`action`, not tuples** — tuples raise `TypeError: tuple indices must be integers`). Lead the section with the `pillar_bar_chart()` (worst-first) and a `rag_summary()` bar so the reader sees the shape of results before reading the rows. **⚪ items never appear in the body** (user rule, 2026-07-09): no scorecard rows, no comparison-table rows, no pillar-table rows, no "not assessed" clauses inside assessed rows — the body grades only what was measured. Everything unassessable goes to the appendix **Footnotes** section, each entry naming what would include it next time (the scope grant). The pillar table shows assessed pillars only, with a one-line footnote pointer for the excluded ones. **Customer-facing reports never show pillar weights** (report-audiences.md) — call `pillar_summary_table(doc, scores)` with **no weights argument** (the Weight column is omitted when weights are absent; a live 2026-07-28 customer report shipped the 20/15/10% weights because the old signature required the dict — caught only on manual re-read). The weights-bearing call belongs to the INTERNAL report's scoring-derivation section only. **And use one grade vocabulary per document:** for customer-facing reports pass `labels=docx_style.EXTERNAL_LABELS` to the table helpers and use the same map for the cover grade label — `docx_style.grade()`'s built-in labels are the internal vocabulary, and mixing them is silent ("C — Building" on the cover, "B — Solid" in the table, same live run).
5. **Deep-dive findings** — one H2 per theme, ordered worst-first. Each must **interpret, not report** (see Phase 4): *What we measured* → *What it means* (the conclusion, from cross-correlation — not a restated definition) → *Effect if unaddressed* (the do-nothing cost: silent degradation, incident exposure, dependency cascade) *and the upside of fixing it* → *Evidence* (the numbers, with method note: which command, what window) → *Remediation steps* (concrete and sequenced, not one vague action). Use `finding_section(...)` with `means=` and `consequence=`, and pass `action=` a list of steps. A finding that stops at a number + definition is unfinished. **And every counted claim carries its own reproduction evidence** (CLAUDE.md core directive #4): pass `reproduction={"query": ..., "note": ..., "sample": {...}}` — the DQL that produced the count, and/or five of the things counted (`{of, columns, rows, caption}` for a table, or a plain list of five strings). It renders directly under *What we measured*, where the reader meets the number. The scaffold refuses to build a finding without it and the hygiene scan fails a counted measurement with no reproduction beneath it, so this is a gate, not a guideline. Cap samples at five; the full list lives behind the query.
6. **Underused capabilities** — the FAQ-12 §4 mapping table: recommended capability | measured state | handicap | action. **Fill "measured state" from the plane probes** (traces B17, databases B18, OTel B19, Kubernetes B20/B21, RUM B22/B23, synthetic B24, SLO B25, AppSec B26/B27, mobile B29) — each row pairs the capability with what the tenant's own data shows and the specific handicap FAQ-12 names for leaving it off. Where the cascade (Phase 4 point 3) shows a withheld rung degrading the rungs above it, state that dependency in the handicap cell, and flag the AppSec-prerequisite and RUM/SLO-history traps in the rows they apply to. This section is the priced-decision version of "we've always done it that way."
7. **Priority action plan** — sequenced 30/60/90-day (or now/next/later) list with owners where inferable.
7b. **Re-measuring after each change** (mandatory) — **the check lives with the finding it supports, not in a list at the end** (owner rule, 2026-08-03). Every ⚠️/💡 finding already carries its client-runnable query in `reproduction`, directly beneath the number it reproduces, which is where the reader meets it and where it is useful during the readout. This closing section carries only what has no single finding to sit under: GUI-only states (masking rule status, extension configuration counts), cross-cutting notes (cost guardrails on log windows, the directional-estimate caveat, setting the environment context), and the standing instruments — the open-source Dynatrace Tenant Review + Platform Adoption dashboards (github.com/dynatrace-oss/CustomerSuccess) and the Discovery & Coverage app. **Never author an entry that repeats a query a finding already shows.** A document that prints the same query twice gives the reader no signal about which is authoritative; `build_reports.partition_verification` drops an exact repeat at build time and reports a near-restatement (≥60% token overlap) so it gets folded into its finding instead — a report of a drop is a findings module to fix, not a build to ignore. Checks are DQL-first (verify the *effect*, not the settings object), read-only CLI one-liners only where no Grail surface exists, cost guardrails embedded, required read scopes stated, and each names where to validate and remediate in the Dynatrace UI (app names + Settings search terms — see the GUI map in [verification-queries.md](verification-queries.md)). **Author each entry as `[label, query, note]` — three elements, the query on its own** (the two-element `[label, how]` form still builds, and the scaffold splits it, but a heuristic split is not a contract). The query is rendered as a monospace shaded code block, because it is copied out and pasted into a Notebook: set as body prose a pipeline reflows into a run-on sentence and the reader cannot see where the query ends and the guidance begins (this shipped in customer deliverables on 2026-07-31). Put the scope requirement, the interpretation hint, and the GUI path in `note`, never inside the query string. **Multi-line queries keep their line breaks** — break long pipelines at the `|` so the block reads as a pipeline.
8. **Appendix** — method (client-safe per the hygiene rules below), **Footnotes — items not assessable in this review** (the ⚪ list lives here and only here, in plain language with the scope grant that would include each next time), **References** (two-part per [bpn-library.md](bpn-library.md) rules: authoritative docs.dynatrace.com pages per finding, then BPN further-reading entries), and the standing disclaimer: *"Community tool, not officially supported by Dynatrace. Figures extrapolated from short sampling windows are marked derived; re-measure before cost forecasting."*

### Client-facing hygiene — what stays internal

The document states **what** was measured, **how** (method, window, date — credibility), and what was **not assessed** — as plain scope statements. It must never expose internal machinery:

- Internal scope/hold decisions and their reasons: *"on hold pending a Grail surface"*, *"out of scope by design"* → write *"not assessed in this review"* (+ the scope grant that would include it next time, when actionable for the client).
- Run-state mechanics: `runs/` paths, `run.json`, probe IDs, resume/diff features, evidence file names in parentheses. Traceability lives in the run file; the report says *"raw measurement outputs are retained and available on request."*
- Raw API error strings (`NOT_AUTHORIZED_FOR_TABLE`, HTTP 500 bodies) → plain language: *"not readable by the review credentials"*.
- dtctl context names and tool-architecture decisions ("100% dtctl, no REST"). Naming the CLI + read-only + auditor is fine; internal design rationale is not.
- Customer-specific engagement material (prior internal assessments, design-review notebooks) — see [bpn-library.md](bpn-library.md): facts with neutral attribution, never named documents.
- **Cross-tenant references — NEVER (user rule, 2026-07-10): no tenant may learn that other tenants were evaluated.** Every report is fully self-contained to its tenant. Banned: "in this review series", "the strongest/best/first ... reviewed", "unique in this series", "other tenants", rankings, or any comparative claim across engagements. Superlatives must be **absolute statements about this tenant** ("an unusually broad set of capabilities", "an actively maintained update setup") — generic industry framing ("many estates get this wrong") is fine; series-relative framing is not. This applies even between tenants of the *same* customer unless the customer-side audience explicitly spans both.

**Pre-delivery check (mandatory, by deliverable type):** after building, scan **every docx this run produced** — paragraphs AND table cells. **The scan is implemented, not prose-derived: run `.dt-eval-common/verify_docx.py <file.docx> --profile internal|summary|detailed`** (`external` is an alias for `detailed`; the sibling skills use `gen3`/`consumption`/`detailed` per the report-audiences.md profile table; the shared `build_reports.py` scaffold calls it automatically and fails the build on findings; a hand-written build script must call it too — re-deriving marker regexes from the prose below each run is how "noise penalty" nearly shipped in a live customer method note). **Whenever the scanner or its marker lists change, re-sweep the tenant's delivered back catalogue with `verify_docx.py <dir> --profile <p> --sweep`** — a pattern fix protects future builds only; four already-delivered files were found dirty exactly this way.

**Distribution marking is mandatory on every page of every deliverable, and the audience decides only WHICH mark** (owner directive 2026-07-31). It lives in the page header/footer, never the cover alone — a cover notice is one paragraph on page one, so a page photographed, pasted into a deck, or printed on its own carried nothing.
- **Everything whose filename carries the `[INTERNAL ONLY]-` prefix** (INTERNAL REPORTs *and* the Executive Summary — the filename is the audience decision, not the voice) carries **`DYNATRACE INTERNAL — NOT FOR CUSTOMER DISTRIBUTION`** in **red** (`C00000`, deliberately not the palette RED that means grade D) in **both the header and the footer** of every page. The footer keeps its version/page/date line underneath — internal readers reference pages by number in discussion.
- **Everything the customer receives** carries the **`AI Generated Evaluation`** watermark: a diagonal grey shape plus a small grey header line. The header line is not decoration — these reports are dense with filled tables, and behind-content shapes are invisible on exactly the pages most likely to be screenshotted.
- Built via `docx_style.new_report_doc(internal=True|False)`; `internal=None` builds an unmarked document and the scan fails it. `internal_banner()` / `ai_watermark()` are idempotent, so a retrofit pass cannot double-stamp.

**Five checks bind every profile and sit outside the audience lists** (like the structural and C7 checks) — the first two were prose rules nothing enforced until a delivered report broke them:
- **`gen2-expansion`** — remediation that extends or creates a **classic (Gen2) construct** (auto-tag/tagging rules, management zones, alerting profiles, problem notifications, classic notifications/dashboards/tags/metric events). Gen3-first: score the outcome capability on its platform-native mechanism and remediate at source (cloud tags / host groups / OneAgent host metadata → primary Grail tag → segment), because a compute-side auto-tag never reaches the Grail record and so can back neither a segment, an IAM security context, nor a DQL dimension filter. **Describing, counting and retiring classic constructs stays legal** — the mz2seg plan is entirely about zones — the check is scoped to an expansion verb near a construct with no contrast cue ("rather than extend …", "never create …", "every new alerting profile added now deepens …") before it.
- **`internal-banner-missing-header` / `-footer` / `internal-banner-not-red` / `watermark-missing`** — the marking above, checked per section in the real header/footer parts, plus `marking-first-page-override` and `marking-odd-even-headers`: a separate first-page or odd/even header silently drops the marking from the page every reader sees first.
- **`foreign-customer-name` / `foreign-org-name`** — hard rule 5 in its **name** form. The cross-tenant list catches the vocabulary of comparison; it could not catch a customer NAME used as a baseline ("matching the *<other customer>* settings baseline"), which is the violation even with no comparative word near it. The roster of other customers is read at scan time from the delivery tree (`<output-root>/<customer>/…`) — local, uncommitted, never in this repo — and any unknown organization carrying a legal-entity suffix is flagged too. The subject is inferred from the file's place in that tree; `build_reports.py` passes it explicitly (`--customer` on the CLI) so a redirected build still runs the check instead of silently skipping it.
- **`graded-headline-external`** — a customer-facing edition carrying a grade badge, an `x/100` or labelled **score** headline, an A–D band legend, or a table column headed Score or Grade, on a run that did not ask to be graded. A **progress** headline (Gen3's "Migration Completeness: 68%" — distance to a target the tenant can reach and be finished with) is exempt. **Grades are an option, never automatic on a customer-facing document** (CLAUDE.md hard rule 7): pass `--grades` to the builder AND to the scan for a run the engagement asked to grade. Keyed on the profile rather than the filename, so the Summary — filed `[INTERNAL ONLY]-`, but customer-facing and score-free by mandate — is covered; `internal` is the exempt profile.

The profiles:
- **INTERNAL REPORT:** cross-tenant markers — benchmark language only, **not the statistical word** (a bare `percentile` pattern flags every legitimate "LCP at the 75th percentile" and pushes the analyst to damage correct prose or ignore the scan): match `percentile of (customers|tenants|enterprise|estates|organi[sz]ations)`, `\d+(st|nd|rd|th) percentile (across|among|compared)`, `industry average`, `benchmark against`, plus `peer (group|benchmark|comparison|percentile|median)` (a bare `peer` false-fires on network topology prose like "fails over to a local peer"), `cohort`, `other customers` — alongside run-state mechanics (`run.json`, `runs/`, `NN-*.json`, raw error tokens), and `$` adjacent to measured customer numbers. Assert the cover carries the internal-distribution subtitle. (Scoring math, KPI names, table names, and statistical percentiles are permitted here — that is the point of the internal producer.)
- **Summary (customer facing):** full scan — internal markers (any internal document names/codenames, `on hold`, `run.json`, `runs/`, raw error tokens, `NN-*.json` evidence names) **and cross-tenant markers** (`review series`, `in this series`, `other tenant(s)`, `any other reviewed`, `unique in this`, comparative superlatives like `strongest posture`/`best measured`) — assert zero before handing over.
- **Detailed (customer facing):** full scan — same as Summary above (internal markers and cross-tenant markers) **plus scoring-machinery markers, scoped to the machinery and not the English word** (a bare `weight` pattern flags ordinary prose like "ordered by the weight of the change" — the failure mode is the analyst then rewriting correct sentences to appease the scanner): match `pillar weight`, `weighted (mean|total|score)`, `weight column`, `Weight %`, `contribution`, `noise penalty`, `Foundation gate`, `derivation` (a customer-facing Detailed report carries scores and grades but never the scoring internals — a live 2026-07-28 report shipped the pillar Weight column and passed the old scan) — assert zero before handing over. A scoped pattern that still fires on legitimate prose is a scanner bug to fix, never a reason to reword a correct sentence.

**Path construction is implemented once — `report_builder._build_output_path` (called by `ReportBuilder`/`build_reports.py`)**: it applies the flat `<customer>/current/` folder and the tenant-first, audience-prefixed filename, plus the atomic `(vN)` reservation; a hand-written build script calls it (or `ReportBuilder`) rather than re-deriving the convention from prose — restated paths are how a live run wrote to a flat legacy layout after the convention changed. **The `(vN)` scan counts the `_superseded/<date>/` folder (a sibling of `current/`) as well as the target folder** (`report_builder.next_version_number`), so versions stay monotonic per stem+date and are never reused: a scan of the target folder alone sees the low numbers as free once earlier editions are filed away, and writes a NEWER document as `(v1)` beside an existing `(v3)` — that happened twice in a delivery folder on 2026-07-29 and had to be renamed by hand.

**Always pass `--run run.json` to the scan.** It enables the mandatory-security-finding check: when this run redacted a credential (A15 webhook secrets or a credential embedded in a webhook URL — `redact.py` exits 2 to say so), the deliverable MUST disclose the tenant's cleartext credentials, per [security-sensitive-data-policy.md](security-sensitive-data-policy.md). Omitting the flag **skips** that check rather than satisfying it. Redacted *email addresses* alone (A18) never trigger it — that is an appendix acknowledgement, not a mandatory finding, and firing on it would train the operator to wave the scan through.

After saving, **verify**: reopen each built file with python-docx, assert paragraph/table counts are non-zero, run the appropriate pre-delivery scan for each file type, and print the section headings. Then report to the user: the **full resolved output path** (`<output-root>/<customer-name>/current/…`, so it is obvious where the files landed — especially when a non-default location was used this run), which deliverable(s) were built (INTERNAL REPORT / Summary / Detailed), the headline score + grade with confidence flag (for Detailed/INTERNAL reports only), the top 3 actions, and anything that was ⚪ (with the scope needed to close it).
